C++ 的 Vibe Coding：让 AI 写代码，但别让它替你负责

一、先说清楚 vibe coding 是什么

这个词是 Andrej Karpathy 在 2025 年 2 月提出的，原话是"完全顺应感觉，拥抱指数级变化，甚至忘记代码本身的存在"。

但这句话被大量误读了。Karpathy 本人是专家，他描述的是"一个专家故意不用自己的技能，看看 AI 能走多远"——这是一种实验姿态，不是一份操作指南。

更准确的理解是：vibe coding 不是盲目接受 AI 的建议，而是进入一种人机同步的心流状态——AI 处理机械性的部分，你专注于架构、逻辑和需要人类判断的决策。就像结对编程，只不过你的搭档永远不会累、读过比你多得多的代码、打字无限快、对自己的建议毫无 ego——但它也会产生幻觉、缺乏上下文、无法推理你的业务需求。

真正的技能在于：知道什么时候让 AI 开车，什么时候自己握方向盘。

二、C++ 为什么是 vibe coding 最危险的语言

这是本文最想讲清楚的一点。

大多数语言里，AI 生成代码出错的后果是"报错、崩掉、你能立刻知道"。Python 里写错了，最多浪费你半小时调试。

C++ 不一样。它的失败模式是静默的：

语言 AI 代码出错的后果
Python / Web 抛异常、报错、崩掉，立刻知道
C++ 静默内存损坏、悬垂引用、数据竞争，跑一个月正常，上线后偶发崩溃

举个具体的例子。std::thread 对象在可 join 的状态下被析构（既没调 join 也没调 detach），会直接触发 std::terminate 让整个程序崩溃。这个设计是故意的——如果默认帮你 join，可能死锁；如果默认 detach，线程会变成野线程，资源无法释放。

AI 生成多线程代码时，大概率会忘记加 join。这种错误在压测时未必复现，但用户端就是无法定位的偶发崩溃。

数据也印证了这个担忧。Veracode 从 2025 年 7 月开始的系列报告显示，早期 45% 的 AI 生成代码样本未能通过安全测试，引入了 OWASP Top 10 漏洞。虽然到 2026 年 10 月，整体安全通过率已从 56% 提升到 62%，漏洞率从 44% 降到 38%，Claude Opus 5.5 和 GPT-6-Sol 以 73% 并列领先——但请注意，这依然是每四份代码里就有一份有问题。

斯坦福大学的研究还发现了一个更隐蔽的问题：AI 助手会让用户对自己代码的安全性产生过度自信。在 SQL 注入测试中，使用 AI 助手的参与者有 36% 写出了易受攻击的解决方案，而不用 AI 的对照组只有 7%。

三、核心工作流：Brainstorm → Spec → Build

这是目前社区验证最有效的节奏，三步缺一不可。

第一步：Brainstorm——把模糊愿望聊清楚

AI 不怕任务复杂，怕边界不清晰。这一步不要让它写代码，只让它读代码、理解现状。

在 prompt 里明确写"先不要修改任何文件，只输出你的理解和方案"：

读取 /src/network 目录，理解当前连接管理和心跳机制的实现。
说明：消息发送的完整链路是什么？连接断开后重连逻辑在哪？
不要修改任何文件。

跳过这一步是最常见的错误。让 AI 在没建立上下文的情况下动手，后面全是返工。

第二步：Spec——把共识落成文字

这一步是 vibe coding 从"许愿"变成"协作"的分水岭。

与其说是写文档，不如说是你和 AI 在开工前按下的同意键。让 AI 主动采访你，是个被严重低估的技巧：

我想给客户端添加离线消息队列功能。
先采访我：问技术实现、边界情况、性能权衡。
不要问显而易见的问题，深挖我没想到的难点。
把结论写成 SPEC.md。

SPEC.md 里至少要明确四件事：数据结构（用什么容器、是否持久化）、并发模型（哪个线程写入、哪个消费、锁粒度）、生命周期（对象谁拥有谁借用、断开连接时怎么处理）、验收标准（怎样算完成、压测指标是多少）。

第三步：Build——一次只做一个验收项

最容易犯的错是把整份 spec 直接丢给 AI。

更稳的节奏是：一次只实现一个验收项，跑通就提交，再进入下一步。AI 后面改坏了，最多退回上一小步，不会一路退化回一团乱麻。

按 SPEC.md 实现第 1 项：MessageQueue 的入队和出队接口。
要求：

  • 写单元测试，覆盖空队列、队列满、并发入队三种情况
  • 运行测试并修复失败项
  • 用 -fsanitize=address,undefined 编译后跑一遍测试

提供验证标准是提升质量最有效的单一动作。没有验证标准，AI 会生成"看起来对但实际跑不通"的代码。

四、C++ 专属：用工具替代肉眼审查

这是 C++ 开发者相对其他语言开发者的巨大优势——内存错误可以被工具自动抓出来，不需要你逐行审查 AI 代码。

固定这一条编译命令，所有 AI 生成的代码都过一遍：

g++ -std=c++23 -Wall -Wextra -Werror -g
-fsanitize=address,undefined
src/*.cpp -o client
./client

工具 抓什么 备注
ASan (address) 越界、悬垂指针、use-after-free 最常用
UBSan (undefined) 未定义行为、有符号溢出 和 ASan 可同时用
TSan (thread) 数据竞争 不能和 ASan 同时用，单独跑

并发部分必须单独用 TSan 跑一遍。AI 生成的并发代码最容易出锁序问题和数据竞争，而这些在压测时未必复现。

五、审查分层：不同风险不同深度

不是所有 AI 生成的代码都需要同等深度的审查。

风险等级 对应什么 审查策略
高 网络收发、线程同步、内存池、序列化 逐行读，重点看生命周期和锁序
中 UI 组件、配置解析、日志模块 看核心路径 + 边界条件
低 文案、样式、CMake 配置、注释 跑通即可

高风险部分有一条经验法则：AI 生成的代码，你至少要能复述出 80% 的逻辑。做不到就让它逐行解释，直到你能复述为止。

审查时问它三个问题，C++ 的坑基本都在这三个里：

  • 这段代码里每个对象的生命周期是什么？谁拥有，谁借用？
  • 两个线程同时调用这个函数会发生什么？
  • 这里可能抛异常吗？抛了之后资源怎么释放？

值得注意的是，vibe coding 的 review 和传统 code review 侧重点不同：代码风格可以快速浏览（AI 通常风格一致），但逻辑正确性、边界条件、安全漏洞、性能问题、架构合理性都要重点检查。AI 常常忽略边界情况，倾向于生成"直观但低效"的代码，而且不了解你的整体架构设计。

六、上下文管理：把项目说明书喂给 AI

这是让 vibe coding 可持续的最重要配置。每次会话开始时 AI 会自动读取这个文件，相当于给它的"项目说明书"。

针对 C++ 项目，建议这样写：

编译与验证

  • 标准：C++23
  • 必须开启：-Wall -Wextra -Werror
  • 调试构建必须带：-fsanitize=address,undefined
  • 并发模块单独用 -fsanitize=thread 验证

架构约定

  • 网络层统一走 /src/net，不直接调用 socket API
  • 所有共享状态必须用 std::mutex 保护，禁止裸原子变量做复合操作
  • 对象所有权用 unique_ptr 表达，禁止裸 new/delete
  • 回调函数不得持有 shared_ptr 形成循环引用

禁止事项

  • 禁止用 reinterpret_cast 做类型双关
  • 禁止在析构函数中抛异常
  • 禁止跨线程传递裸指针

什么该写、什么不该写：

✅ 写进去 ❌ 不要写
AI 猜不到的编译命令 AI 能从代码里读出来的内容
与默认值不同的代码风格 标准语言规范
项目特有的架构决策 详细的 API 文档（给链接）

有开发者在 Windows C++ 项目里还总结了一条经验：在配置文件里明确要求 AI 使用宽字符（wchar_t）和 UTF-8-BOM 编码保存源文件。因为 AI 默认行为往往跟 Windows 的默认编码打交道，一不留神就埋雷，等上线后发现文件名乱码、日志乱码再回头找原因，成本极高。

七、什么该交给 AI，什么不该

这是 vibe coding 最核心的分工问题。

低 AI 价值任务（需要人类判断）：系统架构决策、技术栈选型、理解业务需求、调试微妙的竞态条件、安全威胁建模。

高 AI 价值任务（模式匹配为主）：样板代码生成（CRUD、表单校验）、格式转换、为已有代码写测试、文档和注释、正则和一次性脚本、有明确模式的重构。

最好的 vibe coder 把脑力花在低 AI 价值任务上（人类判断重要的地方），把高 AI 价值任务委派出去（模式匹配为主的地方）。

对 C++ 项目来说，这个分工尤其清晰：

  • 你负责：模块划分、接口定义、线程模型、生命周期设计
  • AI 负责：接口内部实现、样板代码、错误处理分支

构建脚本是个例外，可以放心交给 AI。写 Makefile、CMake 脚本、清理脚本这类东西既枯燥又容易出错，但逻辑相对固定，AI 容易理解，出来的结果也稳定，不像业务代码那样上下文复杂、反复修改后容易引入奇怪的 bug。

八、几条要守住的红线

第一，提示词越具体，代码越安全。 研究发现，查询 AI 助手的提示词越专业具体（例如提供帮助函数或调整参数），生成的代码越安全。

不要说："把消息格式转换成适合传输的格式"
要说："输入是 {id: 1, text: 'hi', ts: 1234567890}
输出应该是 4字节长度前缀 + protobuf 序列化的字节流"

多线程代码尤其如此。如果你只是说"帮我写一个多线程程序"，AI 大概率会忘记加 join；但如果你明确要求"确保在 std::thread 析构之前正确调用 join 或 detach，避免未定义行为"，它就会生成安全的代码。

第二，不要给 AI 太多代理权。 斯坦福的研究发现，提供不安全代码的开发者不太可能主动修改 AI 助手的输出或调整参数。这意味着不能给予 AI 助手太多的自主权（例如自动参数选择），因为这样可能会导致用户疏于防范安全漏洞。

第三，原型 ≠ 生产代码。 vibe coding 的原型作为概念验证是成功的，危险在于把它当成生产就绪的代码。上线前必须过一遍安全审查：有没有硬编码密钥、有没有未验证的输入直接拼进命令、依赖库有没有已知漏洞。

第四，持续扫描，不要只做末端审查。 行业观察者的建议是：随着团队用 AI agent 加速项目，工作流中的持续扫描——而不只是末端审查——对控制风险累积和技术债至关重要。

第五，代码可以交给 AI，问题定义不能。 做什么、给谁用、做到什么程度算完成——这三件事只有你能决定。

九、遇到问题的排查套路

报错改了又错、越改越乱——这通常是"幻觉修复"，AI 为了消除一个报错，编造了不存在的 API 或配置项。

应对方法：不要盲目接受它的修改，让它先解释根因。

先解释这个报错的根本原因，再说明你的修改为什么能解决它。
如果你不确定某个 API 的用法，直接说不确定，不要猜。

如果它解释含糊，大概率是在蒙，这时候去查 cppreference 官方文档。

AI 做出来的不是我想要的——多数时候是提示词信息不完整，或者你依赖了 AI 对模糊词的默认理解。给具体例子，比抽象描述效率高一个量级。

十、最后

Vibe coding 不是"让 AI 替你写代码"，而是"你定义问题，AI 帮你实现，工具帮你验证"。

对 C++ 来说，这句话的后半段尤其重要。这门语言的复杂度是真实的，没有任何人第一遍就能写对——包括 AI。但 C++ 也有别的语言没有的优势：Sanitizer 能把内存错误自动抓出来，-Werror 能把警告变成错误，这些工具不依赖你的经验水平，也不依赖 AI 的可靠性。

所以合理的姿势是：把架构决策和生命周期设计牢牢握在自己手里，把样板代码和实现细节交给 AI，然后用编译器工具链做最后一道防线。

三者缺一不可。少了第一个，代码跑起来但不是你要的；少了第二个，效率没有提升；少了第三个，你会在上线三天后收到用户的崩溃报告。
